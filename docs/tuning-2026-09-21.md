# Two-Spark hardware campaign — 2026-09-21

This campaign targets aggregate throughput with a **64K configured context**.
It is a separate experiment from the original 262K production receipt: the
workloads, thinking-mode handling, output lengths, and cold-start repetitions
are different. Do not divide these numbers by the README's historical numbers
and call that a controlled speedup.

The main measured improvement is admission capacity: the new profile runs sixteen
short requests simultaneously, versus ten before. At twelve clients, mixed-task
active throughput increased from **82.68 to 101.16 tokens/s (+22.3%)**, and coding
from **98.52 to 137.22 (+39.3%)**. Single-request speed changed little. Smaller
batches did not improve consistently; all regressions are retained below.

## Configuration and observed bottleneck

Both nodes used the same verified checkpoint at
`9e0d74e3cef17f634e84fb8e2223707e02616290` and image
`sha256:36eefbfd9f1470c09c3cff70de5cbfbd5d40b6fdda0f018e7298cdeb5cafffa1`.
All 130 checkpoint files matched across nodes (194,692,687,003 bytes).
The image's source label is
`adbf224a6ab47e28c8fd6112efc8e8ee80d9bb14-dirty-6333f64d10a8`;
later changes to launchers and benchmark scripts do not change that identity.
The Dockerfile, compatibility overlay and compiled FlashInfer patch were
unchanged throughout the comparison. Each new receipt records harness hashes.

Hardware/software: two GB10 GPUs, 121.69 GiB usable unified memory per node,
20 CPU cores per node, driver 580.173.02, CUDA 13.0, vLLM
`0.1.dev20051+g487ecf187`, FlashInfer 0.6.17, PyTorch 2.13.0+cu130.
The serving PyNccl communicator used NCCL 2.30.7; PyTorch reported 2.29.7.

The eager control used MTP3, 12 maximum sequences, an 8,192-token batch budget,
64K context and memory utilization 0.82. Its 4.02 GiB cache admitted only ten
short requests: hybrid/MTP state consumed about 9.7% of cache per request.
At C12, two requests waited even with unused compute capacity. The reported
virtual KV token count did not expose this admission limit.

The graph candidate changes **three engine settings together**: CUDA graphs,
16 maximum sequences, and memory utilization 0.85. Startup reported 7.43 GiB
available KV memory on the head and 6.28 GiB on the worker; actual graph storage
was 0.25 / 0.22 GiB respectively. These are per-rank allocations, not a 7.43 GiB
effective cache on both ranks. Sixteen short requests ran simultaneously at
99.1% cache occupancy. These are combined-profile results, not an isolated
measurement of CUDA-graph acceleration. Long prompts consume additional cache
and can reduce admitted concurrency.

## Reproduce the candidate

Start from `config/cluster.env.example`, edit each node's paths and actual
network addresses, and apply the following overrides on both nodes. Generate
the separate template with `scripts/prepare-chat-template.py` first as described
in [the tuning guide](tuning.md). Build once and distribute the exact image.

```bash
PROFILE=experimental
EXECUTION_MODE=graph
MTP_TOKENS=3
MAX_MODEL_LEN=65536
MAX_NUM_SEQS=16
MAX_NUM_BATCHED_TOKENS=8192
GPU_MEMORY_UTILIZATION=0.85
REASONING_PARSER=glm45
NCCL_HCA_LIST=rocep1s0f0,roceP2p1s0f0
NCCL_CROSS_NIC_VALUE=0
NCCL_CHANNELS=8
NCCL_PROTO_VALUE='^LL128'
CHAT_TEMPLATE_HOST=/absolute/local/deployment/chat-template.jinja
EXTRA_VLLM_ARGS=(--compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY","cudagraph_capture_sizes":[4,8,16,24,32,48,64]}')
```

The two named HCAs had independently verified RoCE-v2 GID index 5 on these
machines. Interface names and GIDs must be checked on another installation.
No CPU pinning, power-limit changes, clock overrides, or swap/sysctl changes
were retained. CPU affinity to the faster ten cores produced inconsistent
results and was rejected.

Both fabrics were selected by the real serving communicator. Dual-link large
all-reduce reached approximately 20 GB/s, versus 9–13 GB/s on one link. In the
serving PyNccl microbenchmark, the selected channel/protocol settings reduced
1 MiB eager all-reduce from about 542 to 77 microseconds. This does not establish
an equivalent improvement in model throughput.

## Measurement method

The screening runs use temperature zero, seed 17, distinct request prefixes,
one warm-up wave and two measured waves, with 256 generated tokens per request.
Counting and coding send the same task to different clients; mixed traffic
cycles through twelve different tasks. Active-decode throughput excludes time
to first token; end-to-end throughput includes the entire batch wall time.
Rates at concurrency greater than one are aggregate rates, not one-user speed.

Both compared profiles use the same explicit empty-thinking assistant prefill
for their non-thinking benchmark prompts. This avoids comparing the original
checkpoint template's broken flag-only behavior against the corrected template.
The candidate's ordinary chat API is checked separately without that workaround.
Default requests still enable High reasoning.

The sample is small: tail latencies and differences of a few percent are
provisional. C8 showed intermittent whole-wave first-token delays in both
profiles. There was only one cold start per engine configuration in this
campaign; the original production campaign's two-cold-start claim does not
apply here. Fixed-length generation measures performance, not completed-task
quality. Complete answer checks are separate.

Machine-readable, sanitized measurements are under
[`results/2026-09-21`](../results/2026-09-21/). They retain per-request timings,
wave-level metrics, synthetic payload hashes, configuration and original receipt
SHA256. Deployment addresses, user paths and host names are omitted. Original
private receipts and logs are preserved on the deployment machines.

## Correctness and limits

The pinned checkpoint's template ignored `enable_thinking=false`, while the
parser honored it; ordinary API calls could return concatenated reasoning and
answers (for example `391391`). The separate adapted template fixes the initial
assistant prefix for that mode. The original checkpoint bytes are untouched.
Default/High rendering and prior conversation/tool messages matched in 48
rendering checks. The candidate passed live arithmetic in both modes and a
automatically selected tool call through ordinary chat requests.

Both GPUs passed packed FP8 attention reference checks for H32/H64 at query
lengths 1, 2, 64 and 65, with unequal scales and partial sparse lengths.
Maximum absolute error was below 0.0026 and relative L2 below 0.000564.
These numerical and API smoke tests do not establish broad model-quality
equivalence to a full-precision model.

Marlin remains the MoE backend. Native FP4 backend experiments must first
preserve this model's SwiGLU clamp behavior; swapping in a faster kernel with
different activation semantics is not a valid optimization. MTP depths other
than three and independent graph/cache ablations remain unmeasured here.

The candidate also passed exact two-value retrieval at **8,087 and 59,802 actual
API prompt tokens**, completing in 5.90 and 33.86 seconds respectively. This
qualifies one approximately 60K prompt, not sixteen simultaneous long contexts.
A streamed High-reasoning arithmetic answer had separate nonempty reasoning,
correct final content, a normal stop and the SSE completion marker.

A complete interval-merging function passed execution tests for overlapping,
touching, empty, negative and invalid intervals, sorted output and input
immutability in both modes. Completion took 3.98 seconds without thinking
(130 generated tokens) and 6.26 seconds with High thinking (187 generated tokens).
Generated code ran in a temporary CPU-only, network-disabled container without
host mounts. This is one coding smoke test, not a coding-ability evaluation.

## Serving telemetry and selection

The candidate completed **601 synthetic throughput requests including warm-ups**
across the screen, mixed, High-reasoning and follow-up runs. All streams completed
successfully. Both containers remained running with zero restarts and no OOM
kills; serving metrics reported zero preemptions.

Across the approximately 29-minute measured serving interval, median GPU busy time
was **96% on both nodes**. Minimum host available memory was 8.99 GiB on the head
and 10.40 GiB on the worker. Swap-out counters did not increase; some existing CPU
pages were read back from swap. Model-loading swap activity is excluded from
these serving deltas.

Peak sampled GPU temperatures were **85°C / 83°C** during the approximately 60K
prefill, above the typical short-prompt decode temperatures around 72–75°C.
Separate loaded spot checks showed no active thermal or power throttle flags;
these flags were not continuously sampled. See the sanitized telemetry summary
for the interval, sample counts and exact measurements. Busy percentage does not
measure utilization of peak theoretical FLOPS.

This is the selected profile for the tested shared-throughput workload, with
64K context and High reasoning by default. It does not establish a global optimum,
a latency improvement at every batch size, or long-duration production stability.

## Operational scope

This profile keeps the runtime and checkpoint pinned and requires separate
per-node configuration. Containers use coordinated manual startup; automatic
cross-node restart supervision is not supplied by this change. Keep rollback
configuration and stopped prior-model containers until the deployment is accepted.
The startup-hook failure gate identified in the source review still merits an
explicit per-process overlay-installation check in a subsequent runtime change;
this campaign did not alter the compatibility overlay.
